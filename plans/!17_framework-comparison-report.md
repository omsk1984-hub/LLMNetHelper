# Сравнение LLMNetHelper с DeepSeek Harness / LangGraph / CrewAI Flows

**Статус:** финальное аналитическое заключение по плану
[`16_framework-comparison-plan.md`](16_framework-comparison-plan.md).
**Метод:** только факты из кода проекта и документация сравниваемых решений;
прототипы не строились (по согласованию).
**Дата:** 2026-10-24.

---

## 1. Резюме

**Переход на любое из трёх решений не оправдан.** Основные причины:

1. **Стек.** LangGraph (Python/JS) и CrewAI (только Python) требуют полного
   переписывания проекта на C#/.NET. Критический слой
   [`LLMNetHelper.Roslyn`](../src/LLMNetHelper/LLMNetHelper.Roslyn)
   (полный MSBuild + анализ AST + правки кода) не имеет аналога по
   функциональности на Python — `rospy`/`jedi` не дают графа вызовов,
   компиляции и верифицированных AST-правок.
2. **Свой harness уже существует.**
   [`NativeAgentOrchestrator`](../src/LLMNetHelper/LLMNetHelper.Agent/Orchestration/NativeAgentOrchestrator.cs:25)
   — это и есть агентная обвязка с tool-calling циклом, функционально
   эквивалентная DeepSeek Harness, но **без вендорской привязки**: транспорт
   — любой OpenAI-совместимый endpoint
   ([`CustomOpenAiCompatibleClient`](../src/LLMCore/LLMCore.Llm/CustomOpenAiCompatibleClient.cs)).
   Переход на DeepSeek Harness означал бы сузить себе выбор модели ради цикла,
   который уже реализован и покрыт тестами.
3. **Детерминированность.** Текущий проект находится на уровне **L1**
   (жёсткий детерминированный каркас + LLM в ограниченной зоне). На
   LangGraph реально достичь L1–L2, на CrewAI Flows — L1 для каркаса, но
   L3 при использовании Crew. Ни одно решение **не поднимает потолок
   детерминированности выше того, что уже есть**; они лишь предлагают
   другие способы его снизить.
4. **Ценность фреймворков не совпадает с задачей.** Checkpointing,
   human-in-the-loop, визуализация графа, мультиагентность рассчитаны на
   интерактивных и длинноживущих агентов. Ночной батч с фиксированным
   окном, одним прогоном и отчётом в файл этих возможностей не требует:
   восстановление после сбоя здесь — повторный запуск с теми же
   детерминированными запросами, а не resume из чекпоинта.

При этом у сравнения есть полезный выход: **точечные заимствования**
(раздел 7) — валидация structured output, трассировка шагов, идемпотентный
повтор — реализуемы в текущем каркасе без смены стека.

## 2. Карты систем

### 2.1 LLMNetHelper (базовая линия)

| Компонент | Реализация | Детерминизм |
|---|---|---|
| Порядок шагов прогона | 9 фиксированных `IRunStep`, последовательный обход в [`AgentPipeline.ExecuteAsync()`](../src/LLMNetHelper/LLMNetHelper/Running/AgentPipeline.cs:38) | полный — порядок в коде, не в модели |
| Сбор фактов | Запросы Loki/Prometheus зафиксированы в коде, версионируются | полный — LLM не формирует запросы |
| Диагностика | ReAct-цикл [`NativeAgentOrchestrator.DiagnoseAsync()`](../src/LLMNetHelper/LLMNetHelper.Agent/Orchestration/NativeAgentOrchestrator.cs:53): `MaxSteps=8`, `ToolCallLimit=30`, ошибка модели → вердикт `UNKNOWN`, не исключение | ограниченный: модель выбирает инструменты, но в жёстком бюджете |
| Инструменты | Белый список [`ToolRegistry.InvokeAsync()`](../src/LLMNetHelper/LLMNetHelper.Agent/Tools/ToolRegistry.cs:59): отказ вне реестра **до выполнения**, аудит каждого вызова (`ToolCallRecord`) | полный контроль пространства действий |
| Промпты | [`AgentPromptBuilder`](../src/LLMNetHelper/LLMNetHelper.Agent/Orchestration/AgentPromptBuilder.cs:17) — статический текст, версионируется с кодом; домен из конфигурации (`DomainContext`) | полный — прогон воспроизводим |
| Правки кода | Только 2 AST-операции (`ReplaceMethodBody`, `InsertNullCheck`); [`ChangeTransaction`](../src/LLMNetHelper/LLMNetHelper.CodeChange/ChangeTransaction.cs:83): ветка → правка → build → test → commit, откат при любом провале, push запрещён | полный — пространство правок конечное и верифицируемое |
| Хранение | SQLite + миграции, отчёты Markdown/JSON/diff, всё по UTC | полный |
| Тесты | 145 основных + 8 SK-паритетных, офлайн | воспроизводимость зафиксирована тестами |

### 2.2 DeepSeek Harness (агентная обвязка над DeepSeek API)

Рабочее определение (по согласованию с пользователем): собственный цикл
`модель → tool call → исполнение → модель` поверх OpenAI-совместимого API
DeepSeek с нативным tool calling.

| Аспект | Характеристика |
|---|---|
| Модель управления | Свободный ReAct: порядок действий и момент остановки решает модель |
| Tool calling | Нативный, на уровне протокола (лучше, чем разбор JSON из текста, как в `CustomLlmChatClient`) |
| Ограничения | Не встроены: лимиты шагов, белый список, бюджеты — всё дописывается самому |
| Воспроизводимость | Слабая: температура/мысли модели, нет версионирования промптов «из коробки» |
| Привязка | К вендору (DeepSeek); смена модели = проверка совместимости tool-calling |
| Стек | Любой (обычно Python); сам по себе не является фреймворком — это паттерн |

Ключевой вывод: harness над DeepSeek — это **то, что в проекте уже есть**
(`NativeAgentOrchestrator` + `IChatClient`-адаптер), плюс потенциальный
апгрейд транспорта до нативного tool calling. Второе достижимо точечно:
добавить поддержку `tools` в `CustomOpenAiCompatibleClient` — без смены
стека и без привязки к DeepSeek.

### 2.3 LangGraph

| Аспект | Характеристика |
|---|---|
| Модель управления | Явный граф: узлы (функции) + рёбра; состояние — типизированный объект, течущий по графу |
| Детерминизм | Каркас детерминирован; условные рёбра могут маршрутизироваться моделью → L1–L2 в зависимости от проектирования |
| Сильные стороны | Checkpointing (resume, time-travel), human-in-the-loop (пауза/возобновление), визуализация графа, стриминг, параллельные ветки |
| Слабые стороны для нашей задачи | Python/JS — нет .NET; зависимости от экосистемы LangChain; чужие абстракции в горячем пути; checkpointing избыточен для однопроходного ночного батча |
| Стоимость миграции | Переписывание 14 проектов, включая Roslyn-слой без переносимого аналога |

### 2.4 CrewAI (Flows)

| Аспект | Характеристика |
|---|---|
| Модель управления | Flows: событийный каркас `@start` / `@listen` / `@router` с типизированным состоянием — детерминирован. Внутри узлов запускаются Crew: ролевые агенты со свободным делегированием — недетерминированы |
| Детерминизм | L1 для каркаса Flow, L3 при использовании Crew; «чистые» Crew без Flows — L4 |
| Сильные стороны | Быстрое прототипирование мультиагентных сценариев, декларативность, встроенные механизмы памяти/делегирования |
| Слабые стороны для нашей задачи | Только Python; мультиагентность не нужна (одна задача диагностики с инструментами); ролевая абстракция (CEO/Researcher/Writer) не совпадает с доменом SRE-батча; известная проблема воспроизводимости поведения Crew между версиями |
| Стоимость миграции | Полное переписывание + утрата гарантий L1 внутри Crew |

## 3. Матрица «критерий × системы»

Оценки: **●** — хорошо решено, **○** — решено частично / требует ручной
доработки, **○/** — не решено / противоречит требованиям.

| # | Критерий | LLMNetHelper (сейчас) | DeepSeek Harness | LangGraph | CrewAI Flows |
|---|---|---|---|---|---|
| 1 | Детерминированность потока управления (порядок задаёт код) | ● 9 фикс. шагов + ограниченный ReAct | ○/ модель решает всё | ● узлы/рёбра в коде (при L1-проектировании) | ● каркас Flows / ○/ Crew |
| 2 | Детерминированность сбора данных (запросы фиксированы) | ● Loki/Prometheus в коде | ○/ не входит в harness | ● детермин. узлы сбора | ● детермин. узлы Flows |
| 3 | Ограничение пространства действий (белый список, лимиты) | ● ToolRegistry + MaxSteps/ToolCallLimit | ○/ дописывается вручную | ● контроль в рёбрах/узлах | ○/ лимиты Crew слабые |
| 4 | Воспроизводимость ночного прогона (версион. промптов, одинаков. вход) | ● промпты в git, UTC, SQLite-история | ○/ нет механизмов из коробки | ● состояние сериализуемо | ○/ поведение Crew плавающее |
| 5 | Контроль над правками кода (AST, откат, gate тестами) | ● AstPatcher + ChangeTransaction | ○/ всё самому | ○/ только средствами узлов | ○/ нет аналога |
| 6 | Совместимость со стеком (.NET/Roslyn) | ● родной стек | ● язык-независимый паттерн | ○/ Python/JS | ○/ только Python |
| 7 | Стоимость владения (зависимости, апдейты) | ● минимум, MEAI/SK опциональны | ● свой код под контролем | ○ крупная экосистема-зависимость | ○ крупная экосистема-зависимость |
| 8 | Что даёт сверх текущего | — | нативный tool-calling протокол (частично) | checkpointing, HITL, граф-визуализация | мультиагентность, декларативность |
| 9 | Риски миграции | — | низкие (это паттерн, не фреймворк) | ●●● переписывание + Roslyn непереносим | ●●● переписывание + потеря L1 |

Строка 8 требует уточнения: «сверх текущего» у LangGraph/CrewAI —
возможности для **интерактивных** агентов; для ночного батча они или
избыточны (resume, HITL), или вредны (свободная мультиагентность снижает
детерминизм без выигрыша).

## 4. Уровни детерминированности

Шкала (из плана, раздел 3):

| Уровень | Определение |
|---|---|
| L0 | Полностью детерминированный конвейер, LLM отсутствует |
| L1 | Детерминированный каркас + LLM в изолированных узлах с жёсткими бюджетами и схемой ответа |
| L2 | Детерминированный граф, маршрутизация между ветками может решаться моделью |
| L3 | Детерминированный событийный каркас, внутри — свободно ведущие себя ролевые агенты |
| L4 | Свободный агентский цикл: порядок действий определяет модель |

### Оценки

| Система | Сейчас / как построено | Диапазон «что можно построить» | Обоснование |
|---|---|---|---|
| **LLMNetHelper** | **L1** (гибрид: внешние шаги — L0, зона диагностики — ограниченный ReAct) | L0–L1 | Порядок шагов, запросы, промпты, инструменты и правки — в коде и в git. Модель свободна только внутри `DiagnoseAsync`, и то под `MaxSteps`/`ToolCallLimit`/белым списком. Ошибка модели деградирует в вердикт `UNKNOWN`, а не в сбой прогона |
| **DeepSeek Harness** | — (паттерн) | **L4 по умолчанию; L1 при полном ручном воспроизведении лимитов** | Сам по себе harness ничего не гарантирует: ни лимитов, ни белого списка, ни версионирования. Чтобы получить текущий уровень, придётся заново написать ровно то, что уже лежит в `ToolRegistry`/`AgentPromptBuilder`/`ChangeTransaction` |
| **LangGraph** | — | **L1–L2** (потолок совпадает с текущим) | Граф даёт выразительный детерминированный каркас; но как только маршрутизацию вешают на модель (условное ребро с LLM-решением) — это L2, ниже текущего. Checkpointing повышает отказоустойчивость, но не детерминированность содержательных решений модели |
| **CrewAI Flows** | — | **L1 (каркас Flow) … L3/L4 (Crews внутри)** | Flows-скелет детерминирован, но вся агентная ценность CrewAI — в свободных ролевых агентах, то есть сознательном спуске к L3. Детерминированный CrewAI-Flow без Crew — просто pipeline на Python, проигрышный .NET-варианту |

### Главный вывод по детерминированности

**Потолок детерминированности у всех трёх решений не выше текущего L1.**
Переход мог бы дать не повышение уровня, а лишь:

- лучшую **инфраструктуру** того же L1 (граф-визуализация, чекпоинты) —
  избыточно для однопроходного батча;
- более **нативный tool-calling** (DeepSeek-формат) — достижимо точечным
  апгрейдом транспорта в `LLMCore.Llm`;
- **снижение** уровня (L2–L4) — прямо противоречит принципу
  «детерминированный ночной прогон» (`docs/architecture.md`, принципы 1–4).

## 6. Сценарии, при которых переход всё же оправдан (триггеры пересмотра)

Пересматривать вывод следует при наступлении любого из условий:

1. **Интерактивный режим.** Появится спрос на диалог с оператором
   («а покажи, почему такой вердикт») с паузами и возобновлением →
   checkpointing LangGraph становится потребностью, а не оверинжинирингом.
2. **Смена корпоративного стека.** Команда/организация переходит на Python
   как основной язык → аргумент «переписывание» теряет силу, Roslyn-слой
   всё равно придётся заменять (например, на `tree-sitter` с потерей
   семантической верификации).
3. **Мультиагентность как требование.** Диагностика начнёт требовать
   параллельных специализированных агентов (лог-анализ, код-анализ,
   инфраструктура) со сложной координацией → Crew/LangGraph-supervisor
   начинают окупать свою стоимость.
4. **Утрата поддержки .**NET-обвязки.** MEAI/SDK-экосистема деградирует так,
   что поддержка собственного транспорта дороже миграции.
5. **Визуальная отладка графа становится регулярной.** Если профиль
   инцидентов усложнится до десятков веток, граф-нотация LangGraph даёт
   наблюдаемость, которую сложно воспроизвести в логах шагов.

Ни одно из этих условий сейчас не наступило; проект работает в исходном
сценарии «ночной батч → отчёт → (опционально) ветка с правкой».

## 7. Точечные заимствования без смены стека

Рекомендуемый «переход» — не миграция, а выборочное усиление:

| # | Заимствование | Откуда | Как ложится в проект |
|---|---|---|---|
| 1 | Нативный tool-calling протокол (вместо разбора JSON из текста) | DeepSeek/OpenAI API | Расширить `CustomOpenAiCompatibleClient` поддержкой `tools`/`tool_calls`; `NativeAgentOrchestrator` уже абстрагирован — `IAgentTool.ParametersJsonSchema` мапится в схему инструмента |
| 2 | Валидация structured output JSON-схемой (строгая схема диагноза + повторный запрос при нарушении) | LangGraph `response_format`/pydantic-узлы | Усилить `TryParseDiagnosis`: при невалидном JSON — одна ретрая-подсказка модели, затем `UNKNOWN` (сейчас — немедленный fallback) |
| 3 | Трассировка шагов как «граф» прогона (run → steps → tool calls в SQLite, читаемый журнал) | LangGraph checkpoint-метаданные | Таблица в `SqliteFactStore` + запись `ToolCallRecord`/времени шагов; `RunContext` уже содержит всё необходимое |
| 4 | Идемпотентный повтор шага (skip уже выполненного шага по `runId`) | LangGraph resume | В `AgentPipeline` — отметка завершения шага в БД до перехода к следующему; повтор прогона продолжает с первого незавершённого |
| 5 | Типизированное состояние прогона | CrewAI Flows state | `RunContext` уже играет эту роль; при росте — выделить immutable-снапшоты между шагами для отладки |

Оценка: пункты 1–4 — дни работы в существующем коде; любая миграция на
фреймворк — недели-месяцы с регрессией по детерминированности и потратой
145+8 тестов.

## 8. Итоговая рекомендация

1. **Оставить стек и оркестрацию как есть.** Текущий L1-каркас
   (`AgentPipeline` + `NativeAgentOrchestrator` + `ToolRegistry` +
   `ChangeTransaction`) покрывает задачу ночного батча с гарантиями,
   которые ни один из трёх кандидатов не повышает.
2. **Не мигрировать на DeepSeek Harness** — это регресс к L4 без
   вендорной выгоды; единственный полезный элемент (нативный tool-calling)
   заимствуется в транспорт точечно.
3. **Не мигрировать на LangGraph/CrewAI** — цена (переписывание,
   непереносимый Roslyn, чужие абстракции) не окупается возможностями,
   не имеющими потребителя в батч-сценарии.
4. **Выполнить заимствования 1–4 из раздела 7** по мере приоритета.
5. **Пересматривать решение** при наступлении триггеров раздела 6;
   фиксировать их наступление в `docs/runbook.md` как архитектурное
   решение, а не как имплицитный сдвиг.
