# Скилл: SOLID-аудит решения C# через roslyn-refactor MCP

Цель скилла — воспроизводимая методология аудита архитектуры и кодовой базы
решения C# (`.slnx`/`.csproj`) с обязательным использованием инструментов
MCP-сервера `roslyn-refactor` и оформлением результата как поэтапного плана
улучшений в `plans/`.

Рекомендуемый режим выполнения: **Architect** (только чтение + план в `.md`).

---

## Фаза A. Подготовка и проверка окружения

1. Найти файл решения: `list_files` по корню, искать `*.slnx` или `*.csproj`.
2. Проверить работоспособность MCP-сервера:
   `diagnose` с `solutionPath` = абсолютный путь к решению, `verbose: true`.
   Ожидание: `healthy: true`, `solutionLoaded: true`, известны
   `projectCount` и `documentCount`. Если решение не загружено — аудит
   невозможен, сообщить пользователю.
3. Проверить чистоту компиляции:
   `get_diagnostics` с `severityFilter: "Warning"` (без ограничения по файлу).
   Зафиксировать все предупреждения/ошибки как входные данные аудита.

## Фаза B. Инвентаризация абстракций и контрактов

Прочитать (`read_file`) все файлы-интерфейсы и модели из проекта
Abstractions/Contracts — это каркас, по которому оцениваются ISP/DIP/LSP:

- все `I*.cs` (интерфейсы сервисов, репозиториев, клиентов);
- все `*Models*.cs`, `*Options*.cs`, record-модели;
- композиционный корень: `Program.cs`, `DependencyInjection*.cs`,
  `*Registration*.cs` — карта DI и место поиска Service Locator.

Ключевые вопросы на этом этапе:

- Есть ли в контрактах `IReadOnlyList<object>`, `object`, `string` там,
  где должен быть типизированный доменный тип или `enum`?
- Есть ли `IDisposable`/методы инициализации в интерфейсах, навязывающие
  реализацию всем наследникам (LSP)?
- Сколько методов в интерфейсе и смешивают ли они разные сущности (ISP)?
- Смешаны ли в интерфейсе запросы и команды (CQS)?

## Фаза C. Трассировка потоков данных (поиск дефектов)

Для каждой предметной области, названной пользователем (оркестрация,
промпты, Git, правки кода, отчёты, разбор ответов LLM и т.п.):

1. `find_references` по ключевым типам (модели результатов, интерфейсы) —
   получить полный граф использования.
2. `read_file` производителей и потребителей данных.
3. Проверить типовые дефекты маппинга/сериализации:
   - **потеря типа**: коллекция объявлена как `IReadOnlyList<object>`,
     производитель кладёт `JsonElement`/анонимные объекты, а потребитель
     фильтрует `item is T` → данные молча теряются;
   - **двойная сериализация**: рендерер возвращает готовую JSON-строку,
     а писатель принимает `object` и сериализует повторно (в файл попадает
     строка в кавычках);
   - **несогласованные контракты**: один и тот же вход (например ответ LLM)
     обрабатывается двумя парсерами с разной валидацией — разный результат
     на разных путях;
   - **sync-over-async**: `.Result` / `.Wait()` на асинхронных вызовах
     (`search_symbols` / `codebase_search` по `\.Result`);
   - **semantics misuse**: метод с узкой семантикой (например
     `WriteSnapshotAsync`) используется для записи артефактов другого рода.
4. `find_callers` для подозрительных методов — подтвердить, что дефектный
   путь реально исполняется, а не мёртвый код.

## Фаза D. Метрики кода (SRP, god-классы, крупные классы)

> **Важно:** инструментов `find_large_classes` / `find_god_objects` в
> MCP-сервере `roslyn-refactor` **нет** (проверено по списку `capabilities`
> из `diagnose`). Их заменяет связка `get_code_metrics` +
> `get_document_outline`, дающая те же данные: цикломатическую сложность,
> число строк, индекс сопровождаемости, зацепление и глубину наследования.

1. Составить список кандидатов: `list_files` по исходным проектам, выбрать
   файлы сервисов, оркестраторов, хранилищ, точек входа, циклов/сессий
   (всё, что не является чистой моделью/интерфейсом).
2. `get_code_metrics` по каждому файлу-кандидату. Для точечной проверки
   конкретного класса/метода — тот же инструмент с параметром `symbolName`.
3. Пороги внимания:
   - цикломатическая сложность (CC) > 25 — кандидат на декомпозицию;
   - индекс сопровождаемости (MI) < 20 — плохо, < 15 — критично;
   - связность (class coupling) > 20 — подозрение на нарушение DIP;
   - строк кода (LOC) > 300 — кандидат на звание god-класса;
   - глубина наследования > 2 — проверить хрупкость иерархии (LSP).
4. Для каждого проблемного класса `get_document_outline` — посмотреть список
   методов и оценить, сколько разных ответственностей смешано. Полезны
   фильтры: `kindFilter` (Method/Property/Field), `accessibilityFilter`,
   `nameFilter` — сужают выдачу до нужного среза.
5. Итог фазы — таблица «класс / CC / LOC / MI / coupling» для плана.

## Фаза D2. Нарушения инкапсуляции

Проверенные рецепты (инструменты протестированы на решении проекта):

1. **Публичные поля** (грубое нарушение инкапсуляции):
   `search_symbols` с `kindFilter: "Field"`, `accessibilityFilter: "public"`.
   Пустой результат — нарушений нет. Для полей с `internal` повторить с
   соответствующим фильтром.
2. **Изменяемое публичное состояние доменных типов**:
   `get_document_outline` по файлу модели с `kindFilter: "Property"` и
   `accessibilityFilter: "public"` — свойства с сеттерами в контекстах/
   моделях признак mutable shared state (пример: `RunContext` с 14
   публичными изменяемыми свойствами).
3. **Состояние, протекающее между прогонами**: у зарегистрированных
   singleton-сервисов проверить приватные изменяемые поля через
   `get_document_outline` с `kindFilter: "Field"` и чтение файла.
4. **Мёртвый код и неиспользуемые члены**:
   - `get_diagnostics` с `diagnosticIds: ["CS0169","CS0414","IDE0051","IDE0052"]`
     (неиспользуемые поля/члены);
   - `find_references` с `includeDeclaration: false` — 0 ссылок означает
     неиспользуемость объявления.
     > `safe_delete` в MCP-сервере **неработоспособен**: и `preview: true`,
     > и `allFiles: true` падают с `INTERNAL_ERROR` (неконвертируемый
     > `bool?`). Удаление — только вручную после проверки ссылками.
5. **Проверка иерархий**: `get_type_hierarchy` с `direction: "Both"` —
   базовые типы, наследники и интерфейсы; глубокие или пустые иерархии —
   материал для фазы E (LSP).

## Фаза E. Проверка нарушений SOLID и антипаттернов

Систематический обход по чек-листу (использовать `codebase_search` /
`search_symbols` / `read_file`):

### SRP
- Классы из фазы D: перечислить ответственности каждого.
- Шаги пайплайнов: не делает ли шаг чужую работу (например генерация отчёта
  закрывает прогон)?

### OCP
- Проверки конкретного типа: поиск `is ConcreteClass` / `as ConcreteClass`
  там, где объявлен интерфейс.
- Зашитый порядок: порядок шагов/обработчиков определяется порядком
  DI-регистраций, а не декларативно?
- Парсинг форматов, зашитый в исполняющий класс (новый формат = правка
  класса вместо добавления парсера)?

### LSP
- `IDisposable`, обязательная инициализация и другие требования контракта,
  которые не каждая реализация может честно выполнить.
- Временнóе зацепление: вызов обязан происходить в определённом порядке,
  не выраженном типами.

### ISP
- Жирные интерфейсы (>7 методов разных сущностей).
- Смешение запросов и команд в одном интерфейсе.
- `object`/строки вместо доменных типов в сигнатурах.

### DIP
- Конструкторы принимают конкретные классы вместо интерфейсов
  (`get_symbol_info` по конструктору или чтение файла).
- `new ConcreteClass(...)` внутри прикладных классов (а не в композиционном
  корне).
- Разрешение конкретных типов через контейнер:
  `GetService<Concrete>()` / `GetRequiredService<Concrete>()` вне
  композиционного корня = **Service Locator**.

### Антипаттерны
- **Дублирование логики**: одинаковые приватные парсеры/хелперы в разных
  классах (`search_symbols` по имени метода — несколько определений).
- **Singleton с состоянием**: зарегистрированные singleton-сервисы с
  изменяемыми полями (журналы, кэши) — состояние протекает между прогонами.
- **Магические строки**: вердикты/статусы строками без `enum`.
- **Статические классы-сервисы**: `static` парсеры/рендереры/билдеры
  промптов — не подменяются в тестах.
- **Mutable shared context**: изменяемый объект-контекст, передаваемый
  между шагами, с null-forgiving (`!`) в потребителях.

## Фаза F. Тестируемость

- `list_files` по тестовому проекту: какие области покрыты, какие нет.
- Классы без интерфейсов и со статическими зависимостями = нетестируемы.
- Проверить, есть ли паритетные/контрактные тесты у параллельных
  реализаций одного контракта (например два оркестратора).

## Фаза G. Оформление результата

Создать/обновить план в `plans/` (markdown). Обязательная структура:

1. **Результаты аудита**
   - что уже хорошо (существующие паттерны) — таблица;
   - подтверждённые дефекты — таблица: дефект, механизм, ссылки на файлы
     с номерами строк;
   - нарушения SOLID — по одному разделу на букву, таблицы со ссылками;
   - антипаттерны — таблица;
   - метрики проблемных классов (CC/MI/coupling) — таблица.
2. **Целевая архитектура** — mermaid-диаграмма (без кавычек и скобок внутри
   квадратных блоков).
3. **Поэтапный план**. Порядок этапов обязателен:
   - Этап 0 — неотложные дефекты (без изменения структуры);
   - Этап 1 — типобезопасность домена (enum вместо строк, типизированные
     коллекции);
   - Этап 2 — интерфейсы и DIP (извлечение интерфейсов, сегрегация жирных);
   - Этап 3 — устранение дублирования и стандартизация циклов/движков
     (с паритетными тестами ДО рефакторинга);
   - Этап 4 — декомпозиция god-классов и устранение Service Locator;
   - Этап 5 — пайплайн/контекст (явный порядок, неизменяемость);
   - Этап 6 — тестируемость и сериализация (интерфейсы вместо статических
     классов, единые опции сериализации, контрактные тесты);
   - Этап 7 — архитектурные улучшения (транспорт, нативные механизмы).

   Для каждого этапа указать: **цель**, **конкретные изменения** (таблица
   со ссылками на файлы), **затронутые области**, **критерий готовности**,
   **влияние на существующее поведение**, **риски**.
4. **Зависимости этапов** — mermaid-диаграмма.
5. **Глобальные критерии готовности** — список.
6. **Сводка рисков** — таблица: риск, этапы, мера.

Правила оформления:

- Каждая ссылка на код — кликабельная: ``[`Имя`](относительный/путь.cs:строка)``.
- Без оценок трудозатрат по времени.
- Каждый этап должен завершаться прогоном тестов решения и отдельным
  коммитом.

## Типовые команды инструментов (шпаргалка)

### Анализ (только чтение)

| Задача | Инструмент |
|---|---|

| Структура файла с фильтрами по виду/доступности/имени | `get_document_outline` kindFilter / accessibilityFilter / nameFilter |
| Сигнатура, члены, XML-документация | `get_symbol_info` (+ kindFilter, accessibilityFilter) |
| Граф использования типа/члена | `find_references` (+ accessibilityFilter, includeDeclaration) |
| Кто вызывает метод | `find_callers` |
| Реализации интерфейса/виртуального члена | `find_implementations` |
| Базовые типы, наследники, интерфейсы | `get_type_hierarchy` direction=Both |
| Переход к определению (в т.ч. partial-классы) | `go_to_definition` |
| Поиск символов по имени/виду/доступности/пространству имён | `search_symbols` |
| Поиск по смыслу | `codebase_search` |
| Точный текст/паттерн | `search_files` (regex) |
| Достижимость и точки выхода в сложном методе | `analyze_control_flow` |
| Чтение/запись/захват переменных в регионе кода | `analyze_data_flow` |
| Мёртвый код (безопасное удаление, предпросмотр) | `safe_delete` preview=true |

> Инструментов `find_large_classes` / `find_god_objects` в сервере нет —
> крупные классы ищутся через `get_code_metrics` (см. фазу D).

### Рефакторинг (для фазы реализации плана, применять в режиме Code)

| Задача | Инструмент |
|---|---|
| Исправление нарушения инкапсуляции: поле → свойство | `encapsulate_field` |
| Извлечение интерфейса из класса (DIP) | `extract_interface` |
| Извлечение метода (SRP-декомпозиция) | `extract_method` |
| Извлечение базового класса / перенос членов по иерархии | `extract_base_class`, `pull_members_up`, `push_members_down` |
| Замена конкретного типа на базовый/интерфейс в ссылках | `use_base_type` |
| Перенос типа в отдельный файл / другое пространство имён | `move_type_to_file`, `move_type_to_namespace` |

| Синхронный метод → async (устранение sync-over-async) | `convert_to_async` |
| Добавление проверок аргументов (надёжность контрактов) | `add_null_checks` |

предпросмотр, затем применение. В режиме Architect изменения не применять.

## Извлечённые уроки (из аудита 2026-10-24)

- Дефект «потеря данных при фильтрации по типу» ищется трассировкой:
  производитель → объявленный тип коллекции (`object`) → потребитель с
  `is T`. Обязательно читать оба конца цепочки.
- Двойная сериализация ищется сопоставлением возвращаемого типа рендерера
  (`string`) и типа параметра писателя (`object`).
- `find_references` по record-модели до изменения её сигнатуры даёт полный
  список мест, которые затронет правка (оценка риска этапа).
- Если два класса декларируют «семантическую эквивалентность» (комментарий
  в коде), проверять побайтовое совпадение их парсеров — частый источник
  расхождений поведения.
