# Скилл: ручное выполнение SOLID-плана с MCP-проверками и TDD

Цель — реализовать поэтапный план из `plans/*solid*plan*.md` (созданный
скиллом `solid-architecture-audit`) без регрессий. Ключевой принцип:
**каждый пункт плана — отдельный цикл «красный тест → правка → зелёный
тест → MCP-проверка → коммит»**.

Режим выполнения: **Code**.

---

## 0. Опорные факты о MCP-сервере (проверено эмпирически)

MCP-сервер `roslyn-refactor` — инструмент **верификации**, а не редактирования.
Он закрывает ~20% плана; остальное — ручные правки.

### 0.1. Что работает надёжно (анализ, только чтение)

| Инструмент | Назначение в цикле |
|---|---|
| `find_references` | До правки: полный список мест, которые затронет изменение сигнатуры (blast radius) |
| `find_callers` | Подтвердить, что путь исполняется, а не мёртвый код |
| `get_symbol_info` | Точная сигнатура/члены до и после правки |
| `get_document_outline` | Каркас файла для точных `apply_diff`; поиск публичных полей/свойств |
| `get_diagnostics` | **После каждой правки**: 0 ошибок/предупреждений |
| `get_code_metrics` | **После этапа**: подтвердить снижение CC / рост MI |
| `get_type_hierarchy`, `find_implementations` | Контроль полноты при изменении контрактов |
| `search_symbols` | Поиск дубликатов имён методов/констант по решению |

### 0.2. Что работает как рефакторинг (подтверждено preview)

| Инструмент | Статус |
|---|---|
| `convert_to_async` | Работает с `preview: true`: меняет сигнатуру и обновляет все вызовы (проверено: 3 вызова). Использовать для пунктов «устранить sync-over-async» |
| `move_type_to_file` | Preview создаёт файл и удаляет объявление, **но `referencesUpdated: 0`** — межпроектные ссылки не обновляет. Использовать только вместе с ручным `add_missing_usings`/правкой using, либо не использовать вовсе |

### 0.3. Сломанные инструменты (известный баг сервера)

Падает с `INTERNAL_ERROR: The JSON value could not be converted to
System.Nullable'1[System.Boolean]` при передаче булевых параметров:

| Инструмент | Параметр | Ошибка |
|---|---|---|
| `rename_symbol` | `preview: true` | `$.preview` |
| `extract_interface` | `preview: true` | `$.preview` |
| `safe_delete` | `preview: true` | `$.preview` |
| `safe_delete` | `allFiles: true` | `$.allFiles` |

При этом `convert_to_async` и `move_type_to_file` с тем же `preview: true`
отрабатывают — значит, дефект в схемах конкретных инструментов, а не в
способе вызова. `safe_delete` неработоспособен полностью (оба булевых
параметра падают), поэтому для поиска мёртвого кода использовать
`find_references` с `includeDeclaration: false`.

**Правила обращения со сломанными инструментами:**

1. **Не вызывать их без `preview`** — изменение применится сразу, откат
   только через git.
2. Если нужен предпросмотр — заменить вызов ручной правкой:
   - `rename_symbol` → `find_references` (получить список мест) + серия
     `apply_diff` по каждому файлу;
   - `extract_interface` → прочитать публичные члены через
     `get_symbol_info` (с `kindFilter: "Method"`), написать интерфейс
     вручную, добавить `: IName` в класс;
   - `safe_delete` → `find_references` с `includeDeclaration: false`:
     0 ссылок ⇒ удалить объявление вручную.
3. Перед любым применением без preview — убедиться, что рабочее дерево
   чистое (`git status --porcelain` пустой), чтобы откат был атомарным.

### 0.4. Чего MCP не умеет в принципе (всегда вручную)

- менять тип члена record (`IReadOnlyList<object>` → `IReadOnlyList<Finding>`);
- писать логику маппинга/парсинга (new code);
- добавлять новые методы и вызовы к ним (например `Reset()` в реестр);
- переносить куски логики между классами (согласование валидации);
- менять три скоординированных файла одновременно (контракт → реализация →
  вызывающий);
- писать тесты.

## 1. Подготовка

1. Прочитать план (`plans/…`), выписать пункты текущего этапа в todo
   (`update_todo_list`) — по одному пункту на элемент.
2. Убедиться, что рабочее дерево чистое:
   `git status --porcelain` → пусто. Если не чисто — спросить пользователя,
   как поступить (не коммитить чужие изменения).
3. Базовый прогон тестов ДО любых правок:
   `dotnet test src/LLMNetHelper/LLMNetHelper.slnx`
   Зафиксировать стартовое число пройденных/упавших/пропущенных.
4. Базовая диагностика: `get_diagnostics` (severityFilter=Warning) —
   зафиксировать стартовый набор.

## 2. Цикл выполнения одного пункта

Повторять для каждого пункта этапа строго последовательно:

### 2.1. Red — тест, фиксирующий дефект

- Найти существующий тестовый файл по области
  (`LLMNetHelper.Tests/<Область>/*Tests.cs`); если нет — создать новый.
- Написать тест, который **падает на текущем коде** и описывает желаемое
  поведение. Имя теста — на русском/английском как в существующих файлах,
  обязательно с комментарием, какой дефект плана он фиксирует
  (например `// Дефект D1: находки теряются при маппинге Diagnosis → AnalysisResult`).
- Запустить точечно:
  `dotnet test src/LLMNetHelper/LLMNetHelper.Tests/LLMNetHelper.Tests.csproj --filter <ИмяТеста>`
  Ожидание: **FAILED**. Если тест прошёл — дефект не воспроизводится;
  разобраться (возможно, путь не исполняется — проверить `find_callers`)
  прежде чем править код.

### 2.2. Green — минимальная правка

- До правки: `find_references` по каждому изменяемому символу — полный
  список мест. Править **все** места в одном `apply_diff`/наборе правок,
  иначе решение не скомпилируется.
- Вносить только изменения, необходимые для прохождения теста. Никакой
  попутной реструктуризации (это следующий этап плана).
- После правки:
  1. `get_diagnostics` по затронутому проекту → 0 ошибок;
  2. точечный тест того же фильтра → **PASSED**;
  3. полный прогон `dotnet test src/LLMNetHelper/LLMNetHelper.slnx` →
     не меньше пройденных, чем на шаге 1.3, и 0 падений.

### 2.3. Verify — MCP-контроль

- `find_references` по исправленному символу — убедиться, что нигде не
  осталось старой сигнатуры/мёртвых вызовов.
- Если пункт менял контракт: `find_implementations` — все реализации
  синхронизированы.
- Если пункт удалял/переносил тип: `get_type_hierarchy` — нет «осиротших»
  наследников.

### 2.4. Commit

- Один пункт = один коммит. Сообщение:
  `fix(stage0.<N>): <суть> (план 18, дефект D<M>)`.
- Не объединять пункты в один коммит — это ломает возможность точечного
  отката.

### 2.5. Если пункт не проходит

- Откатывать только этот пункт (`git checkout -- <файлы>`), фиксировать
  причину в плане (`plans/18_solid-improvement-plan.md`, снять галочку,
  добавить примечание), переходить к следующему. Не оставлять полуизменения.

## 3. Завершение этапа

1. Полный прогон: `dotnet test src/LLMNetHelper/LLMNetHelper.slnx` — все
   зелёные (сетевые помечены `Category=Integration` и остаются Skipped).
2. `get_diagnostics` (Warning) — 0.
3. `get_code_metrics` по затронутым файлам — зафиксировать динамику
   (CC/MI/coupling) в плане.
4. Отметить пункты этапа как выполненные в `plans/…md` (галочки `[x]`)
   и добавить строку «Статус: этап N завершён <дата>».
5. Переходить к следующему этапу только после закрытия критериев готовности
   текущего (раздел 5 плана).

## 4. Специфика этапов плана (подсказки)

| Этап | Основной механизм | MCP-опора |
|---|---|---|
| 0 — дефекты | Ручные `apply_diff` + TDD | `find_references`, `convert_to_async` (0.3), `get_diagnostics` |
| 1 — типобезопасность | Вручную: enum + конвертеры на границах сериализации | `search_symbols` по строковым литералам, `find_references` |
| 2 — интерфейсы/DIP | Вручную (extract_interface сломан): писать интерфейс, менять параметр, DI-регистрацию | `get_symbol_info` (члены), `find_implementations` (полнота) |
| 3 — ReAct-цикл | Сначала паритетные тесты, потом перенос кода вручную | `find_callers`, `analyze_data_flow` для региона цикла |
| 4 — декомпозиция | Вручную: выделять классы/обработчики | `get_code_metrics` до/после, `move_type_to_file` с ручной доводкой using |
| 5 — пайплайн | Вручную: `int Order` + сортировка в `AgentPipeline` | `find_references` по `IRunStep` |
| 6 — тестируемость | Вручную: интерфейс + DI-регистрация вместо static | `get_document_outline` |
| 7 — транспорт | Вручную, под флагом конфигурации | паритетные тесты SK/native |

## 5. Запреты

- Не менять поведение без падающего теста заранее.
- Не применять `rename_symbol`/`extract_interface`/`safe_delete` без
  `preview` на грязном дереве.
- Не запускать скрипты как `.\script.ps1` (уйдёт в Блокнот) — только явный
  вызов `pwsh` с UTF-8-префиксом (правило проекта 02-powershell.md).
- Не останавливать никакие процессы без явного разрешения пользователя.
- Не объединять несколько пунктов плана в один коммит.
- Не править исторические/архивные документы в `plans/` как конфигурацию.
